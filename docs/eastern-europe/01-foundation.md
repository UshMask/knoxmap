# ТЗ 01. Архитектура и контрольный участок

Результат этапа — воспроизводимый контрольный проект и проверенная граница `Generate → Build` для следующих изменений. Предыдущий этап — исходное состояние ветки. Далее — [02. Первые улучшения OSM](02-osm.md).

## 1. Зафиксировать контроль

- Использовать сохранённый локальный `kirov_street_test` из `artifacts/kirov-vehicle-zones-20261118`. В его `*_info.json` записаны масштаб 1 м на тайл, поворот 0°, размер 2100 × 3900 тайлов и сетка 7 × 13 ячеек. Взять `c5c26ad` за исходную версию транспорта. Исторический `comparison.json` сравнивает её с `a5c3a20`.
- Сохранить копию проекта для проверок. Зафиксировать commit, `bbox`, проекцию, масштаб, поворот, настройки и `seed`, хеши снимка OSM и прочих использованных входов, версии компилятора и игры. Для быстрых прогонов сохранить небольшой контрольный фрагмент с переходом, домом и двором. Большую карту использовать для сравнения транспорта и повторной компиляции.
- В контрольный набор результатов включить `*_buildings.geojson`, растры земли и растительности, `*_placements.csv`, `*_vehicle_zones.json`, `*_population.json`, `objects.lua` и перечень скомпилированных ячеек. Записать, какие файлы получены вновь и какие взяты из сохранённой сборки.

## 2. Описать и закрепить контракт

Точки входа — [`web/generation.py`](../../web/generation.py), [`generator/renderer.py`](../../generator/renderer.py), [`generator/rendering/buildings.py`](../../generator/rendering/buildings.py) и потребитель [`knoxbuild/build.py`](../../knoxbuild/build.py).

1. Граница первого выпуска — существующий `<name>_buildings.geojson` рядом с `<name>_info.json`. Зафиксировать географические координаты GeoJSON в порядке `[lon, lat]`, преобразование в тайлы через параметры проекта и текущие поля. Добавлять свойства только при появлении потребителя.
2. Зафиксировать совместимость GeoJSON старых проектов с текущим `Build`. Новые необязательные поля без значения оставляют прежний путь вычисления. Для объекта OSM полная идентичность — тип `node`, `way` или `relation` вместе с ID. Привязку редактора к этой паре добавить на этапе, где она впервые нужна. Синтетические здания продолжают использовать текущие правила идентификации.
3. Параметры, геометрию и факты об источнике хранить в данных проекта, используя существующие механизмы сохранения. Для диагностики определить формат сведений, которые понадобятся первому инспектору: объект, поле, значение, источник и признак оценки. Показывать эти сведения по мере реализации конкретных правок.
4. Сохранить обычные команды `Generate`, `Build`, `Compile` и `Install`. Проверить точку инвалидирования кэша при изменении экспортируемых данных. Записи проекта выполнять штатным механизмом, например [`knoxfiles.write`](../../knoxfiles.py) для JSON.

## Контракт текущей реализации

| Файл | Данные, которые использует `Build` |
| --- | --- |
| `<name>_info.json` | Границы `south`, `west`, `north`, `east`, масштаб `meters_per_tile`, размеры в тайлах и ячейках. Необязательный `rotation` по умолчанию равен нулю. `Build` проверяет размеры восстановленной проекции перед размещением зданий. |
| `<name>_buildings.geojson` | `FeatureCollection` с геометрией `Polygon` или `MultiPolygon`, координатами `[lon, lat]` и свойствами здания. В `properties` сохраняется `osm_id`, а для размеченных помещений может присутствовать `rooms`. Этап 02 может дополнять свойства в этих же файлах. |
| Снимок OSM | `osm_cache` с именем снимка относительно папки проекта и `osm_bbox` с границами снимка. Если они отсутствуют, используются `<name>_osm.json.gz` и `bbox` карты. Для старого абсолютного пути приоритет у пригодного одноимённого снимка рядом с копией проекта. Если он отсутствует, повреждён или покрывает другой участок, `Build` проверяет старый путь. Если ни один вариант не подходит, причина указывается в журнале. |

Обычный и разбитый на участки `Generate` сохраняют имя снимка относительно папки проекта, когда он лежит рядом с картой. Входы, точки заведений и бумажная карта читают его по [одним правилам](../../generator/osm.py). На этом шаге сохраняются границы снимка и поддержка старых версий фильтра OSM. Загрузка из сети не выполняется.

Ключ кэша TBX учитывает параметры конкретного здания, которые `Build` выводит из геометрии, свойств и настроек. При изменении входа, влияющего на результат, меняется ключ затронутого здания. Сведения, которые пока служат только диагностике, могут не влиять на ключ.

## Приёмка

- Снимок проекта пригоден для повторного прогона из тех же входов. Для старого проекта непустые и отсутствующие необязательные поля обрабатываются совместимо.
- В двух прогонах с одинаковыми входами совпадают содержательные результаты. Для промежуточных файлов с техническими метаданными сравниваются данные после исключения таких метаданных.
- При переходе к этапу 02 известно, какой файл проверить после `Generate`, что прочитал `Build` и как отличить результат от устаревшего кэша.
